# Changelog

All notable changes to this project are documented in this file.

The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project uses [Semantic Versioning](https://semver.org/): given a
version `MAJOR.MINOR.PATCH`, `MAJOR` marks breaking changes (a data
migration you must run, an env var that's now required, etc.), `MINOR`
marks new features that are safe to pull in without extra steps, and
`PATCH` marks fixes. Until 1.0 the project is on a beta track
(`0.1.0-beta.1`, `0.1.0-beta.2`, … toward each `0.MINOR.0`), described in
[CONTRIBUTING.md § Versioning](CONTRIBUTING.md#versioning-the-pre-10-beta-track).

If you maintain a fork, check this file when you pull in a new release —
see [UPGRADING.md](UPGRADING.md) for the actual update steps.

## [Unreleased]

### Changed

- **Knowing an administrator's email is no longer enough to lock them out (#594).** Failed sign-ins are now counted per address and account: ten failures from one address stop that address, not the real person signing in from somewhere else. A higher ceiling (five times as many, from any mix of addresses) still stops a guesser who keeps changing address, but an address that has signed in with a correct password before (remembered in memory for 30 days) is let through. The same applies to wrong two-factor codes.

### Security

- **A public demo refuses passkeys, and System Info warns about the testing-site setting (#595).** On a public demo a visitor could add up to five passkeys to a shared, published login. Adding one is now refused there (the owner's own test deployment, which sets `DEMO_TESTING_SITE`, is not guarded and can still add them). System Info also shows a warning at the top when `DEMO_TESTING_SITE` is set, because one mistaken setting on a demo the public can reach would end password sign-in for its published logins.

## [0.1.0-beta.4] - 2026-11-27

### Upgrading

- **Every install that ran `0.1.0-beta.3` or earlier must have its database reset, then reseeded (pre-1.0).** The single baseline migration was edited in place and its folder renamed from `20261122092854_init` to `20261127000000_init`. For example: the database now refuses a phone or email that isn't in the saved form (#573), recovery codes for two-factor (#550), one-time needs gain "someone's on it" and "met" (#554), and there are new church settings for the currency (#556), the Scripture passage on the Subscribe page (#553) and skipping the review of verified partners' mail (#551). The app refuses to start on the old database ("Not starting: This database was built from an earlier version of migration ...") and the deploy fails safe, leaving the old version running, until the database is reset. Steps: [UPGRADING.md](UPGRADING.md) and [RUNBOOK.md](RUNBOOK.md). A new install is unaffected.
- **`FIELD_ENCRYPTION_KEY` is now required to start** (it protects two-factor secrets and every saved integration credential). The Render button generates one for a new install; an existing install must set one before updating (`npm run generate-secrets` prints one), and must keep it: losing or changing it locks out everyone who uses an authenticator app.
- **There is no separate worker service any more.** The scheduled jobs and the WhatsApp connection run inside the web service (#522). After updating, delete the old worker service in Render.
- **Sign-in:** the "Passkey sign-in" church setting is gone (the passkey button is always on the sign-in page), and a setup link now signs a new person in at the end. Nothing to do.

### Added

- **First-run setup uses the same choice, then asks for a second administrator (#590, #589).** The first administrator chooses a passkey (no password) or a password and an authenticator app, and is signed in when they finish, with no separate sign-in. Right after, a one-time, skippable "Add a second administrator" screen comes before the public-site question, and the Home reminder stays until there are two. The wording about the authenticator app now says a passkey is offered first.
- **A guided new-account page (#590).** A setup link now opens one page that asks "Where will you mostly sign in?" and signs the person in at the end, in place of choosing a password, signing in again, then setting up two-factor on separate screens. "Mostly on this device" creates a passkey (no recovery codes; an administrator's Reset MFA, or "Email me a new link" on the sign-in page, is the way back). "Different or shared computers" sets a password, then an authenticator app and recovery codes. A plain-words "Why do we ask for two proofs?" explains the request. A link never replaces two-factor an account already has: it only changes the password, and the person signs in the normal way. A new-link request is limited to one every 15 seconds, and the sign-in page says "Lost your passkey, or signing in for the first time? Email me a new link" when the site can send email. The two-factor setup screen is now shared with the sign-in page.
- **A simpler, passkey-first sign-in page (#590).** The sign-in page is now two short steps: a **Sign in with a passkey** button (and the browser's own passkey list in the email box) first, then your email, then your password, or an emailed link where the church signs in without passwords. It looks nothing up before you prove who you are, so it never reveals whether an email has an account. The passkey button is always offered (except on a public demo); the old "Passkey sign-in" checkbox in Manage Users is gone.
- **A nudge to add a second administrator (#587).** A church with exactly one active administrator is one lost phone from a lock-out that only a server command can fix, so the bell and the Home page now say "You are the only administrator" (admins only; it goes away when a second admin is added, and it is not shown on a public demo). The install guide has a new step for it, and the "Locked out of two-factor" section starts with a plain three-step recovery path (recovery codes, then a second administrator's Reset MFA, then the server command).
- **A clear warning when a passkey is used at the wrong web address (#586).** A passkey only works at the one address the site is set to (`APP_BASE_URL`). Opening the site by another (the bare domain instead of `www`, or the old `onrender.com` address after adding a custom domain) used to fail with only "That passkey couldn't be verified" or "didn't work". Now an admin browsing at the wrong address sees a banner naming both addresses, and a passkey that is turned away for that reason says which address to use (the message depends only on the address, never on the account). The guide describes it.
- **A copy button next to phone numbers and emails (#571).** Where people paste a number or an address elsewhere, a small copy button now sits beside it: the contact card (and the go-between's), the care team list, a partner's adults, and a trip participant's and applicant's own, emergency-contact and parent/guardian details. A phone copies in international form (`+15065550259`, which dials from any phone or app) and the button's tooltip says exactly what was copied; an email copies as saved. The click and key presses stay on the button, so it never opens the section or row behind it. It follows the contact rules: nothing is offered for a partner not to be contacted directly, and under caution only for the ways the church ticked.
- **A "Sign out of all devices" button in My Account.** Signing out from the menu ends only the browser you are on. The new button ends every open session signed in as you, on every device, this one included (it raises the account's session number, the same thing a password change does), for after signing in on a shared computer or losing a phone. It asks first, needs no password (it can only sign people out), is written to the audit log, and is not available on a public demo, whose logins are shared.
- **A hint on web addresses and on mailing street addresses.** A web address box (a partner's link, a sending church's website, the church's own website) now shows the web keyboard and, when you leave it, a short note if what you typed can't be saved as a web address (the server already saved "example.org" as "https://example.org" and refused other schemes). The first line of a **mailing** address (a partner's mailing & contact address, a sending church's, the church's own, and the survey's mailing address question) says so when it has neither a number nor a PO box. It is never shown on a serving location, which is often a village with no street. Hints only: nothing is blocked.
- **Restore a backup from inside the app (#501).** Settings → About App has a **Restore from a backup…** button, for a church that can't run the restore command. It replaces everything on the site with the backup, so it first downloads a copy of the current data (so the restore can be undone; the restore refuses to run without one made in the last 15 minutes), then asks for the admin's password again and the word `RESTORE` typed exactly (and the passphrase of a locked file). The uploaded file is kept on disk and read as a stream, never held in memory, and is checked from start to end (checksum, row counts, passphrase, and that it was made for this version of the database) before anything is touched. The replace is one database transaction (any failure leaves everything as it was), every other change to the site is refused while it runs, the scheduled jobs skip their ticks until it finishes, and the result is recorded in the audit log. Admin-only and off on a public demo.
- **Photos load from a smaller copy, and the full photo is kept.** Every partner and trip participant photo now has a display copy (a JPEG at most 800px on its longest side, aspect ratio and phone rotation kept) made when it is uploaded, so the directory, lists and map download a fraction of the bytes. `GET /api/photos/:id` serves that copy (or the full photo when it was already small); `GET /api/photos/:id/raw` serves the full photo as uploaded, with the same access rules, and is what the booklet and "View" / the public detail page's photo link use. The partner API gives `url` (display) and `rawUrl` (full); the public partner gives `photo` and `photoFull`. The church logo is shrunk when uploaded (at most 800px wide, in its own format so transparency survives). Resizing uses `sharp`, one image at a time, and refuses pictures over 100 million pixels (the full photo is still kept and served). New nullable `PhotoBytes.displayBytes` and `TripParticipantPhoto.displayBytes`; **pre-1.0 this is part of the baseline, so a dev or demo database is reset and reseeded** (the seed makes the copies). Backups include the new column automatically.
- **A partner nobody has contacted yet is no longer instantly "quiet", and a partner can be snoozed "not this season" (C8).** My partners, the bell and the care chat posts counted a never-contacted partner as quiet from the first minute, so a new install (or a partner just added) was instantly all overdue. Their quiet days now count from the day they joined the person's list. **Edit contact** also gains **Not this season**: until the chosen day the partner is left out of "quiet" (My partners shows "Not this season until ..."), while a follow-up date someone set on purpose still shows. Staff-only; the public site never carries it. **This changes the baseline migration** (one new `Partner` column), so an existing database needs the pre-1.0 reset described in UPGRADING.md.
- **A church-wide currency setting.** Amounts used to be written with a hard-coded "$" in about ten places (trip money, field labels, one-time need announcements, report headings). **Settings → About & Branding → Church Info → Currency** now sets one currency for the whole app (any ISO 4217 code, default USD): monthly support, one-time needs, trip budgets and contributions, reports (headings and CSV), and GroupMe/WhatsApp/email announcements all follow it. It changes the symbol only; amounts stay whole numbers and nothing is converted, so a church changing it should check its existing figures. Trip money that used to read "$1250" now reads "$1,250". **This changes the baseline migration** (one new `ChurchSettings` column), so an existing database needs the pre-1.0 reset described in UPGRADING.md.
- **The database now refuses a phone or email that isn't in the saved form, and a church can set the country its phone numbers are read in (#548).** Every phone and email column (partner, adult, emergency contact, go-between, sending church, trip participant and application, donor, church contact, account phone) has a database CHECK constraint: a phone is international digits (`+15065550259`), an email has the shape of an address and is at most 200 characters, blank is NULL. The routes already refuse anything else, so this only catches a script or import that writes a column directly. The login email and newsletter signups are not constrained. **Settings → About & Branding → Church Info → Phone numbers without a + are read as** sets the country a number typed without a country code is read in (default United States), so a church in the United Kingdom can type 020 7946 0958; a number that starts with + keeps its own country and nothing already saved changes. The check is length and shape only, so a plain 10-digit American number typed in a UK church is read as a UK number: type the +1. **This changes the baseline migration** (one new `ChurchSettings` column and 28 constraints), **and renames it**: the folder is now `20261127000000_init` instead of `20261127000000_baseline_nov_2026_review`, because the timestamp already says when it was cut, so an existing database needs the pre-1.0 reset described in UPGRADING.md; a number saved earlier in another form is not converted, which is why a reset (and the updated demo seed) is the way through.
- **One-time needs can say "someone's on it" and "met" (#511).** Open a need to record who has taken it on (a person or group, free text) and the day it was met. These are separate from the funding decision: an undecided need with someone on it reads "Someone's on it: …" instead of Pending Decision, a met need reads **Met** whatever was decided (even declined, if it was covered elsewhere), a met need no longer counts as waiting for a decision on My partners, and the One-Time Needs report has a "Where it stands" column (masked for restricted partners). Care team members can set both on their own partners' needs. Neither sends anything. **This changes the baseline migration** (two new `SupportNeed` columns), so an existing database needs the pre-1.0 reset described in UPGRADING.md.
- **The Scripture passage on the public Subscribe page is now a church setting (#508).** The page used to print Ephesians 6 in the ESV for every church. It now shows a passage only when a church sets one (**Settings → About & Branding → Public Site & Branding**: the passage and where it is from), and is empty by default, so each church picks its own translation and checks its licence. A church that liked the old passage can paste it in. **This changes the baseline migration** (two new `ChurchSettings` columns), so an existing database needs the pre-1.0 reset described in UPGRADING.md.
- **A setting to skip the review of inbound mail from a verified partner (#505).** Since every inbound message now waits in Emails to sort, a church that trusts its partners' senders can tick **Settings → Email → Receiving → File mail from a verified partner without review**. Then a message whose sender matches exactly one partner and passes SPF or DKIM is filed as that partner's newsletter and announced at once; anything else still waits. Off by default, since a sender address can be forged. **This changes the baseline migration** (one new `ChurchSettings` column), so an existing database needs the pre-1.0 reset described in UPGRADING.md.
- **Recovery codes for two-factor sign-in, a command to clear it, and a required encryption key (#496).** Setting up an authenticator app now shows ten one-time recovery codes, once, and the person has to tick that they have saved them before carrying on. At the sign-in screen, "I lost my phone: use a recovery code" takes one; My Account shows how many are left and makes a new set (which retires the old ones). Admin **Reset MFA** removes the codes along with the secret. `npm run clear-two-factor -- <email>` (documented in the Admin Guide under "Locked out of two-factor") lets whoever runs the server get a sole admin back in; the first-run page and Manage Users now tell a sole admin to add a second one. **`FIELD_ENCRYPTION_KEY` is now required to start:** the Render button already makes one, but a self-hosted install that was running without it will stop at start-up with a message saying how to generate one. **This release changes the baseline migration** (a new `UserRecoveryCode` table), so an existing database needs the pre-1.0 reset described in UPGRADING.md.
- **A Sunday prayer sheet (C10).** **Prayer sheet**, under Prayer Requests in the menu, makes a one-page printable list of what to pray for, or the same thing as slides for the screen at church (one partner per slide, arrow keys or buttons, Escape to close). Choose how often you make a sheet (every week, every two weeks, or once a month) and the sheets rotate through your partners so each comes round about once a month (weekly shows a quarter of your partners, every two weeks half, monthly all of them); the same Sunday always gives the same sheet, and nothing is stored. Because it is handed out, it follows the public site's rule: only public, unrestricted, unarchived partners, and only their ministry requests marked public that are still ongoing. No schema change.
- **One-time needs can be declined, and don't need a dollar amount (#511).** Record Decision now has a **Decline this request** choice (it records $0 approved, so the need reads Declined everywhere), where before the only way was to know to type 0. A need can also be saved with no requested amount: leave the box blank (it is saved as 0 and shown as "No amount"), including when the AI scan of a letter finds a need that names no figure, which it previously could not add. GroupMe posts and emails say nothing about money for a need with no amount, and say "Declined" without a "$0" line for a decline. The "someone's on it / met" state is a separate change that needs a database update.
- **Downloading a backup asks for your password again, and can be locked with a passphrase (#501).** The backup is the most sensitive file the app makes (every partner, restricted ones unmasked, and every password hash), yet it came down on a bare link. Now the download is a button that asks for the signed-in admin's password (a wrong one is refused and logged), and optionally locks the file with a passphrase of your own: a locked file has a `.locked` ending and cannot be opened without it. The app says plainly that a lost passphrase cannot be recovered, because it is never stored. Unlocked downloads still work. The restore command asks for the passphrase of a locked file. The restore guide no longer suggests a "temporary, unlisted file host" and now says how to move a file safely. Restoring from inside the app is a separate, later change.
- **Trip applications and backup reminders can come by email (#423).** When Email (Sending) is on, a new trip application emails the admins (only admins) with the applicant's name and a link to review it, never their contact details. Admins also get a backup reminder email about once a month, held back for 30 days after they dismiss the in-app one, and off once the reminder is turned off for good. With email off nothing changes: the application is still a bell badge and a row on the trip's Team page, and the backup reminder is still the banner and the bell. Neither is ever sent from a public demo.

### Fixed

- One definition of a "quiet" partner. My partners, its bell item and the care chat's quiet-partner post now start the quiet count again whenever a partner is heard from in any way (a logged contact, a newsletter filed, a prayer request received or a visit to your church), the same four things the Last heard from report counts, instead of the contact log alone. The column is renamed "Last heard from". The grace period and "Not this season" work as before.
- With no public page switched on (directory, map or prayer sign-up), "Show on public site", the "Not public" pills and the Public filter no longer appear on the add-partner form, a partner's page and the Partners list, and the prayer request form offers a single "Include in printed booklet" box instead of "Show on public profile". What was ticked before is kept and returns when a public page is turned on.
- Pages reached only through a private link (a survey, a team member's own trip page, a private trip application link) show the church's name and logo but no longer the public menu (Directory, Map, Trip Opportunities) or "Team sign in", so a partner or team member is not offered pages that are not meant for them.
- The trip application form checks the email on the first step, so a mistyped address is caught there (and the field is flagged) instead of only when you submit on the last step. A link to a trip that has stopped taking applications now says "Applications for <trip> are not open right now" instead of "This trip couldn't be found" (a restricted partner's trip is not named; an unknown link still says not found).
- **"Go to Settings → X" sentences are links (#477 Phase 1, #618).** Seven places told a person to go to a Settings page in plain text: the Updates to Share intro, passwordless sign-in's "turn on email first", the second-administrator step and its link note, the survey send note, the trip's application questions note (a link for admins only; a trip leader can't open Settings) and the public-site choice. Each is now a working link to the page. The two AI scanning errors named "Settings → AI Features", which isn't a page; they now say **Settings → Integrations → AI Features**.
- **Empty lists say what they are for instead of "No … match these filters" (#618, #477 Phase 1).** The Partners and Trips lists and every report said "No partners match these filters" / "Nothing matched those filters" even on a new install with nothing in them and no filter set. They now tell the two cases apart: with filters on, "No … match these filters" and a **Clear filters** button; with nothing added yet, what the list is for and the first step (**+ Add the first missionary** / **+ Add an organization**, **+ Plan the first trip**, or "Nothing to report yet" on a report). The Partners heading no longer says "active" while archived partners are shown ("3 partners, archived included"). Other lists already had their own plain wording.
- **Leaving a phone, email, web-address or street box no longer moves the page, so a tap on Save is not lost (found while testing #618).** The note under those boxes appeared when you left the box, which pushed the button below it away; on a phone the first tap on Save only left the box, and the tap was lost. The note is now laid out, invisibly, as soon as the value would earn one (and not at all for a valid value, so there is no blank gap) and shown when you leave the box (`FieldHint`). Hints still show on leaving the box; nothing autosaves on blur.
- **The backup banner no longer greets a brand-new install (#477 Phase 1).** A new install's first screen was a "This app doesn't back itself up" banner and a bell item, when there is nothing in it yet to lose. Both are now held back for the first 3 days after the first account is created, then appear as before (dismissing still snoozes them for 30 days; the monthly reminder email is unchanged).
- **First-run setup asks for the first administrator's name (#477 Phase 1).** Setup asked only for an email and a password, so every change the first admin made was recorded as "Someone". It now asks for a first and last name (both optional, trimmed, and blank is no name) and saves them on the account; `POST /api/auth/setup` accepts `firstName` and `lastName`.
- **A survey answer is no longer filed under the wrong survey's title on Survey Updates (#618).** A partner's waiting changes are grouped under their name, and the heading showed the first change's survey title for the whole group, so a change from a second survey read as if it came from the first. The heading now names the survey when all the changes are from one, and says "2 surveys" otherwise, with each change naming its own.
- **The partner's survey page saves what it can, and its messages show where they are looking (#618).** "Save and finish later" saved nothing if any one answer was invalid (a mistyped phone number blocked every other answer). It now keeps every valid answer and lists the ones it could not keep, with the reason ("Saved, except for these: Phone: …"); **Submit** and answers entered by staff stay all-or-nothing. The "Saved", "Thank you" and error messages were rendered above the questions, off-screen after pressing a button at the bottom of a long survey on a phone; they now sit beside the buttons and are scrolled into view.
- **Every public page names the church and links team sign-in (#477 Phase 1).** The public header showed only the page title, so a visitor couldn't tell whose site it was, and the team had no way in from the public site. The header now shows the church's name above the title (when one is set) and a **Team sign in** link beside the menu; the "This isn't public" page names the church too.
- **The public prayer sign-up is hidden when it cannot work, instead of answering "Not found" (#618).** With email off (or switched on but not set up) or the public directory off, `POST /api/public/subscribe` refused with "Not found" while the "Pray for our …" link and the sign-up form still showed. The public settings now say whether signing up can work (`publicSubscribeAvailable`: the public prayer digest is on, the public directory is on, and email can really send); the nav link, the `/subscribe` page and the follow form on a partner's page appear only then.
- **"Clear" on Updates to Share asks first and fits a phone, and the approve dialog no longer contradicts itself (#618).** "Clear" deleted a queued update with no confirmation, and its button was cut off the screen on a phone. It now asks ("It will not be sent anywhere, and it can't be brought back"), and Approve and Clear are stacked so both fit at 390px. The dialog for approving a care team member's item said it would go "to your team" and then "to the whole congregation"; both approve dialogs now say it goes out in the chat posts and update emails (and the public prayer digest, if used), with exactly the wording shown, and that it can't be taken back.
- **The bell no longer clears alerts or snoozes the backup reminder just by being opened, and its badge matches its list (#618).** Opening the bell marked every alert seen, so alerts vanished from the badge without anyone acting on them (for an admin the same click also snoozed the backup reminder for 30 days), and the badge, the list and each line counted three different things. Opening it now changes nothing. The badge counts the alerts that are waiting, which is exactly the number of lines in the list; each line still shows its own item count. An alert leaves when what it is about is dealt with (or, for the "new prayer requests" and "new needs" alerts, when you open that page), so the three alerts that never cleared (updates to pass on, trips departing soon, email not finished) no longer show a stuck "new" badge: they show while they are true and go when they are not. The backup banner's own dismiss button still snoozes it.
- **An unknown address shows a page-not-found screen, not a blank page (#618).** There was no catch-all route. An unknown public address now shows "That page wasn't found" with links to the home page and team sign-in; an unknown address under `/admin` shows the same message inside the admin shell with a link back to Home.
- **Key-date controls and settings pages no longer show when their feature is off (#618).** The My partners table kept its "Next key date" column and a "Send greeting" button with Key dates off. The GroupMe, Integrations and Email settings pages opened in full by typed address while their feature was off (Email showed "Couldn't load email settings"); they now say the feature is off, as WhatsApp and Trips already did. That message named "Church Settings › Features", a page that doesn't exist; it now links to **Settings › Enabled Features**.
- **Sections that belong to a feature that is off no longer show (#618).** An organization's page showed an empty "Family & Personal" heading (every card under it is for missionaries). The "Mission Trips" heading, its jump button and Trip Capacity showed on every partner while Trips was off. The prayer form offered "Include in printed booklet" while the booklet was off. They now appear only when they apply.
- **A care team member's edit to a public prayer request no longer goes live unreviewed (follow-up to the fix above).** Removing the public and booklet flags from a care team member's saves (guests and care-team viewers) still let them reword, re-categorise, move or mark answered a request that staff had already made public, and the new text reached the public sheet and booklet with no review. Such an edit (to the wording, category, partner, status or answer note) now takes the request off the public profile, the Sunday sheet and the booklet until staff review it and tick the boxes again. Notes and the source link do not count; staff edits are unchanged.
- **A trip leader's access no longer survives the Trips feature being switched off, and a care team guest is told why (#618).** A guest whose only access was leading a trip could still open that trip's partner and read the full record after Trips was turned off, because trip access was not tied to the switch (the care team seat already was). Trip access is now enforced against the `trips` switch server-side (`resolveGuestReach` in `backend/src/utils/guestAccess.js`, used by `requireAuth`), exactly as a care team seat is against `careTeam`; the grants are kept, and access returns unchanged when the feature is switched back on. A guest left with nothing but a switched-off feature used to be bounced to the sign-in page with no explanation (every request answered 401); now every route except `GET /api/auth/me` answers `403 feature_paused`, and the app shows a plain page, "Trips are paused" or "Care teams are paused", saying their church has paused it and nothing was removed, with no instruction to change a setting they cannot reach (the Trips pages used to say "Turn it back on at Church Settings › Features" to a guest). A guest with both kinds of access keeps the one that is still on. Full read access to a trip and its partner is unchanged while Trips is on.
- **The printed booklet no longer includes restricted partners by default (#618).** On Print Booklet the **Restricted-access** option was ticked when the page opened, so a restricted partner printed with their real name and details unless someone unticked it. It now starts unticked; when ticked, the page says how many restricted partners are included (under the Archived and organizations choices) with a one-line caution. Nothing else about who the booklet includes changed: it is the church's own document and still prints partners whether or not they are on the public site. See UPGRADING.md.
- **A care team member's request can no longer reach the public profile or the printed Sunday sheet unreviewed (#618).** A code comment said a care team member can "never … make anything public", and their entries are held for staff review before posting or emailing, but the create and update routes still let them set **Show on public profile** and **Include in printed booklet**, and the prayer sheet and booklet select on those two flags with no review check. Anyone who is not an admin or editor (a limited guest on a care team, or a read-only viewer who can write only because they sit on that partner's care team) now has both removed server-side on create and update (a request they edit keeps whatever staff chose), the two boxes are not on their form, and saving says "Your request has gone to the Missions team for review" (the church's own name for the group). Admins and editors are unchanged.
- **Prayer requests labelled "Everyday … staff only" are no longer shared (#618).** An Everyday (`situational`) request for a public, unrestricted partner was recorded for sharing like any other, so it was posted to GroupMe and WhatsApp, included in staff email digests and, with the public prayer digest on, emailed to public subscribers. Now no sharing record is made for an Everyday request when it is saved or answered (so nothing queues, shows on Updates to Share, or waits to be released), and the record carries the category and the request's id so a second line refuses it everywhere anyway: every channel's eligibility check (`dispatchEligibility.js`, which the daily chat post, both email digests, urgent send and "review and approve now" all go through), the text builder (so it is never shown in the review queue), and the housekeeping that clears the queue. ## [0.1.0-beta.2] - 2026-11-25

### Security

- **Smaller hardening items from the security review ([#412](https://github.com/neckermann/missions-partner-tracker/issues/412)).** Ids in a trip's child records must belong to that trip (a guest on one trip could attach, overwrite or read another trip's people and requirements through document uploads, flight segments and contributions). The emailed sign-in link is sent at most once a minute per account, so nobody can mail-bomb a person or keep replacing their live link, and only real accounts are audited. A prayer request or need's source file must be the same partner's file. Only staff can log a contact as someone else; a care team guest's entry is always their own. A passkey challenge is accepted once through the database (`SpentPasskeyChallenge`), so that holds across restarts and more than one instance. In production, passkeys need `APP_BASE_URL` (or Render's own URL) and refuse to run without it, rather than trusting the request's Host header.

- **The printed booklet withholds more for a partner who isn't safe to contact ([#411](https://github.com/neckermann/missions-partner-tracker/issues/411)):** their serving and mailing addresses, and their sending church or organization's contact person and phone, no longer print (the names still do). ### Security

- A Trip Leader scoped guest account could still read the full Pending Dispatches queue (`GET /api/dispatches/pending`) — the exact text about to go out for every partner/trip/prayer request/one-time need churchwide, unfiltered and not attached to any one trip. Excluded entirely, same `requireRole("admin", "editor", "viewer")` pattern as #329's inbound-email-queue fix (there's no sensible trip-scoped version of this queue). No database migration. (#350)
- A Trip Leader could re-point their own trip's `partnerId` at any partner via `PUT /api/trips/:id` (the full field set was written straight through with no per-role filtering), then use that attacker-controlled `partnerId` to pass the partner-scope check on every partner-scoped read — the full record of a partner they were never meant to see, restricted partners included. Blocked: a Trip Leader's update is now rejected outright if it includes `partnerId`. (#327 Finding 2)
- `GET /api/trips?partnerId=` returned every trip belonging to that partner, full participant rosters (dates of birth, guardian/emergency contacts) included, when a Trip Leader's own partner had more than one trip on file — not just their own. Now scoped to exactly their own trip, regardless of the `partnerId` query. (#327 Finding 2)
- `GET /api/settings/trips` and `GET /api/scoped-digest/summary` were reachable by a Trip Leader with no role check beyond being logged in — neither has a legitimate use for that role (church-wide trip configuration and a cross-church subscriber-count summary). Excluded. (#327 Finding 2)
- `PUT /api/trips/requirements/:id/participants/:participantId/complete` never checked that `:participantId` actually belonged to the requirement's own trip — a Trip Leader scoped to one trip could mark a different trip's participant complete against one of their own trip's requirements, given a leaked participant id. Fixed by validating the participant belongs to the requirement's trip before proceeding. (#327 Finding 3; the IDOR's other instance, `POST /:tripId/participants/:id/request-documents`, no longer exists — removed along with the trip document-request feature.)
- An unauthenticated caller could fill the database and exhaust memory on several public routes: the global JSON body limit was 15mb for every route (for the sake of one webhook), every string on the public trip-application schema was unbounded with no cap on how many custom-question `responses` a submission could carry, and the public document-upload route buffered up to 15mb into memory before even checking whether the caller had a valid access token. Fixed: the global body limit is now 100kb, with scoped 15mb/7mb exceptions for the three routes that genuinely carry a large payload (the Postmark webhook, and the two base64-image routes); every public application field now has a `.max()`; the two apply routes got a dedicated 10-per-15-minutes-per-IP limiter and a honeypot field; the upload route's access token moved from the request body to the query string so it's verified before the file upload middleware ever runs; a bad-credentials request to the inbound-email webhook no longer writes a database row. (#327 Finding 4)
- A session token kept working for its full 8-hour lifespan regardless of what happened to the account afterward — logging out only cleared the cookie, never the token itself, so a password change, an admin-set password reset, an MFA change, or a role change left every previously-issued session still valid. Added `User.sessionVersion`, embedded in the session token and checked against the row on every request; bumped on password change (self-service and admin reset), MFA enable/disable (self-service and admin-forced), and role change — deliberately **not** on logout, which stays scoped to the one cookie/browser it represents rather than silently signing a user out of every other device. The self-service routes (password change, MFA disable) re-issue a fresh cookie in the same response, so the tab making the change keeps working; only sessions opened elsewhere are the ones actually invalidated. Requires `npx prisma migrate deploy` (new `sessionVersion` column, default 0 — no other migration steps needed). (#327 Finding 7)
- Several fixes from the same pass: production access logs no longer write a usable `token` query-string value in plain text (Postmark/subscribe-link/trip-participant tokens all redacted to `[REDACTED]`); the trip-participant self-service access token (opens a minor's record, donor contact info, flights, and documents) had no expiry at all before this — now expires at the trip's own end date + 90 days (falling back to a flat 1 year when trip dates aren't available, never infinite), re-issuable through the existing lost-link recovery flow if it's ever actually needed again; `password-setup/validate` moved from GET with the token in the query string to POST with it in the body. Three links that changed state the moment they were _fetched_ (a real risk — mail security scanners pre-fetch inbox links) now only act on a follow-up POST: the admin digest unsubscribe link, the public subscriber unsubscribe link, and the meeting-RSVP links each render a plain-HTML confirm button first (still works with no JavaScript, the same constraint that made them GET in the first place); the two unsubscribe flows' outgoing digest emails also carry `List-Unsubscribe`/`List-Unsubscribe-Post` headers (RFC 8058), so a supporting mail client's own native "Unsubscribe" button can act with no page shown at all. (#327 Finding 6, now complete)
- A matching partner's email address alone used to be enough to auto-file an inbound email as that partner's newsletter and broadcast it to GroupMe/WhatsApp/the digest — `From` is trivially forgeable, so anyone who knew a church's inbound address and one partner's email could put a forged document under that partner's name and have it announced unreviewed. Now also checks Postmark's own SPF/DKIM signals (`Received-SPF`, and `X-Spam-Tests`'s `DKIM_VALID` token as a secondary signal) before auto-filing; a single match whose sender doesn't verify is queued for review instead, labeled "Sender not verified" in the Unmatched Emails queue rather than silently guessed. Requires `npx prisma migrate deploy` (new `InboundEmail.queueReason` column, nullable — no other migration steps needed). (#327 Finding 5)
- Three upload paths stored a file's client-declared type without ever checking the actual bytes against it, even though `utils/fileResponse.js` serves a file inline specifically on the premise that this was already checked: the trip-document-requirement upload, the participant self-service photo, and a `.eml`-named partner file (the filename-based `.eml` exemption meant a file named `x.eml` declaring `application/pdf` was stored and later served inline as that type, completely unverified). Added one shared `verifyUpload()` every upload route now calls; a `.eml` is always stored as the canonical `message/rfc822` regardless of what the client declared, never signature-checked (there's nothing reliable to check), and every other declared type is verified against its real magic bytes. (#327 Finding 8)
- `GET /api/settings` used a denylist (`omit` 6 secret columns), so every other column went to any signed-in role, Trip Leader included — `inboundEmailWebhookUsername` (half of the webhook credential), `inboundEmailAddress`, every GroupMe/WhatsApp internal id/name/connection-state field, and anything added to the model in the future by default. Switched to an explicit `select`: a field now has to be deliberately added to ever reach this response. GroupMe/WhatsApp integration detail is already served by their own dedicated admin-gated routes and wasn't read by this endpoint's actual consumers anyway. (#327 Finding 9)
- Re-subscribing an already-confirmed email address used to apply the new cadence/scope immediately with nothing proving the caller actually owns that address — anyone who knew (or guessed) a real subscriber's email could silently re-scope their subscription. Now a change to an already-confirmed subscriber is only proposed: it's emailed to that address as a confirm-change link (distinct copy from the first-time confirmation, so an existing subscriber doesn't read it as "you weren't subscribed before"), and only written to the database if that link is clicked. Still-unconfirmed and brand-new subscribers are unaffected — nothing about their row is "live" yet either way. No database migration; the proposed values travel inside the confirm-change link's own signed token. (#327 Finding 11.2)

### Changed

Each has URL-backed filters, summary tiles, charts, click-through summary tiles, CSV download and print / save as PDF. No database migration.

**Welcome emails with secure password setup.** Adding a user (including a
Trip Leader) now emails them a one-time "Choose your password" link instead
of an admin typing a password. The link is single-use, expires (72 hours;
7 days for Trip Leaders), and only a hash of it is stored. Add User has a
"Send a welcome email" toggle (on by default) and a "Require two-factor
authentication at first sign-in" option; turning the email off leaves the
account pending until a password is set or "Send setup link" is used on its
row. The sign-in-time two-factor setup screen and Account Settings now walk
first-timers through installing and using an authenticator app. Trip
participant emails (meeting invites with Yes/No/Maybe buttons, reminders,
checklist and date-change notices, team welcome) and the new welcome email

`npx prisma migrate dev`. Guide/support links in the welcome email point
at this project's own docs and aren't configurable per fork (no new env
vars).

The notification system is now called **Dispatch** throughout the app
and its database schema, so it can't collide with a future in-app
notifications feature. Nothing about how it behaves changed — "Pending
Notifications" is now "Pending Dispatches," "GroupMe notifications" is
"GroupMe dispatch," the Notification Settings page is now Dispatch
Settings, and so on, across every admin screen and both guides. Under
the hood, every notification-related table/column/file was renamed to
match (see `backend/prisma/schema.prisma` and
`backend/src/utils/dispatch*.js`) — a fork with its own customizations
touching that vocabulary will need to update those references when
pulling this release in.

New **WhatsApp dispatch** option alongside GroupMe: new prayer
requests, one-time needs, and newsletters (plus a prayer request's
answer and a one-time need's decision) can post to their own groups
inside one WhatsApp community. It runs on the same daily send hour and
the same content-type mutes as GroupMe — a church can run either or both
— and several related items go out together in one message instead of
one post each. Off by default, behind a new **WhatsApp dispatch**
feature toggle; set up entirely in the UI (Settings →
WhatsApp): link a dedicated phone number with a pairing code or QR code,
pick the community, then pick a group for each dispatch type.

Worth knowing before turning it on: this is an unofficial connection
(the number is linked the way WhatsApp Web is), so WhatsApp can ban
numbers used this way — use a dedicated number, never a personal one.
The linked session is stored encrypted in the database (it isn't included
in backups, so restoring onto a new instance means linking again), and
sends go through ban-risk protection that spaces messages out and pauses
them if the number looks flagged. Needs one new schema migration
(additive only) and runs inside the existing web service — no new Render
service.

Assigning an email from the **Unmatched Emails** queue to a partner now
lets you pick what kind of file it actually is — Newsletter, Survey
Response, Signed Policy, Email Communication, Office Document, or Other
with your own label — the same choices as uploading any file directly,
instead of always filing it as a Newsletter. Newsletter stays the
default, since that's still what most inbound mail turns out to be.

**Trips** (#252) is a major rework of mission trip tracking into full
recruiting/roster/support-raising support, built on the existing
`Trip`/`TripParticipant` models rather than a second, separate concept.
A trip now has a lifecycle (`planning` → `accepting_applications` →
`closed`/`completed`), public or private application links, a per-trip
roster with meeting invites (real calendar `.ics` attachments) and
document requirements, and per-participant support-raising pages with a
manual donor-contribution ledger. Because this reaches well beyond the
old admin-only Trip History/Trip Opportunities pages into public
application forms and outbound email, the existing **Mission trips**
feature flag now defaults **off** (previously on) — a fork relying on
it staying on for its existing trip-logging needs to flip it back on
once after upgrading. Two new settings gate the feature's public-facing
pieces independently: **Public trip discovery** (the public Trip
Opportunities listing/plain application links — a church can run trips
entirely by private link with this off) and two per-church toggles,
_allow private application links_ and _allow public support-raising
links_, each off by default. A restricted partner's trip is excluded
outright from the public discovery page, but a private application
link or support-raising link for one still works — masked, not blocked —
since reaching either already requires a secret only staff chose to
share. Needs one new schema migration (five new tables, several
renamed/added columns on `Trip`/`TripParticipant`/`ChurchSettings`,
including `Trip.tripType` → `Trip.type`).

Anyone can now opt in to email updates on prayer requests, with no
account needed — either for every partner, several at once, or just
one, from a new public **Subscribe** page, or for a single partner
from that partner's own public page (which also points to the
Subscribe page for anyone who wants more than just that one). Each
subscriber picks weekly, biweekly, or monthly, confirms by
email first (a plain double opt-in, no account), and can unsubscribe
anytime from a link in every email — no admin-managed list. Public
digests are prayer-requests only: never a one-time need, never a
newsletter or a link back to one, and a restricted partner's content
stays masked exactly as it already is everywhere else. Off by default,
behind a new **Public prayer digest** feature toggle; also needs
Public Directory and Email (Sending) turned on.

Admins get the same cadence-and-scope choice for the existing
notification digest, replacing the old all-or-nothing "email me the
digest" checkbox — pick weekly/biweekly/monthly and either every
partner or just the ones you follow, from your own Account Settings.
Unlike the public digest, an admin's digest still includes one-time
needs and newsletters, same as before. A new **Prayer Digest
Schedule** section (Settings → Notifications) sets when
these three cadence tiers actually go out — independent of the
existing schedule, which still only governs GroupMe and the original
church-wide email batch. A new **Prayer Digest Subscribers** page

A new **System Info** page (Settings, alongside Backups)
shows what's actually running on this instance — app version (plus

Node.js/React/React DOM versions, the Postgres version and database

A restricted partner's photo tile in a Snapshot-layout digest email
showed a blank gap instead of the generic silhouette — most email
clients (Outlook chief among them) strip a `data:` URI out of an
`<img src>`, which is how the silhouette was embedded. It's now served

A restricted partner's prayer request or one-time need notification now
needs an admin's manual review before it's eligible to send at all —
held back from both the manual "Send Pending Notifications Now" button
and the automatic digest schedule until someone confirms it. Structural
masking (name → initials, photo → silhouette, no link back to the
source file) stays exactly as it already was either way; this is
scoped to the body text itself, which previously always sent as a
generic "details are withheld" placeholder with no way to include the
real wording even after a human had checked it for anything
identifying.

Reviewing is also just editing — any queued notification, not only a
held restricted one, can have its text tidied up before it sends, with

A missions partner tracker for a single church: who you support, where
they are, what they need prayer for, and what you've given — with a

What's in it:

- **Partners.** Missionaries and organizations are one record type
  distinguished by `kind`, so everything downstream — trips, support,
  prayer requests, newsletters & docs — attaches the same way for both.
  A partner's page is also its editor: each section saves only its own
  fields, so changing one thing can't quietly overwrite another.
- **A public site that protects people.** Partners marked
  restricted-access appear with their name masked to initials, a
  silhouette instead of a photograph, and a map pin coarsened to a country
  centroid. Every public response goes through one masking serializer that
  no public route can bypass, tested in isolation — and the same masking
  carries through to GroupMe posts and digest emails, not just the public
  site.
- **Prayer requests, monthly support, one-time needs, and trip
  history/opportunities**, each with its own page and its own section on
  a partner's page.
- **Newsletters & Docs.** Upload a newsletter, survey response, signed
  policy, email record, or other office document against a partner,
  picking its kind from one list — reclassify a mis-filed upload the same
  way you'd edit anything else, no delete-and-re-upload required.
- **Optional AI Request Scanning.** Point it at an uploaded file and it
  suggests prayer requests and one-time needs for review — nothing is
  added without an explicit accept. Off by default, and only available at
  all once `ANTHROPIC_API_KEY` is set, since it's the one feature that
  sends file content to a third party.
- **A printable booklet** with six selectable Look & Feel templates
  (Classic, Modern, Traditional, Keepsake, Portfolio, Friendly), an
  optional facing Notes & Prayer page, and a configurable cover/back
  cover — built for handing round on paper.
- **Reports.** Read-only views — birthdays, monthly support, one-time
  needs, prayer requests, trip history, furlough — each filterable, with
  CSV export and a clean print layout.
- **Optional GroupMe notifications.** New prayer requests, one-time
  needs, and newsletters post to their own configured GroupMe Topics,
  along with answered-prayer/decided-need outcomes — queued and sent as a
  batch rather than posting the instant they happen.
- **Optional email**, via Postmark — outbound digests of what's queued,
  and inbound email that auto-files a reply as a newsletter when it
  matches a known partner (anything else lands in an Unmatched Emails
  queue for a quick manual assign). Sending and receiving toggle
  independently.
- **Notification batching**, shared by GroupMe and email: review what's
  queued and send it on a schedule or on demand, with an email digest
  customizable between a plain Classic layout and a Snapshot layout
  (partner photo, "supporting since," short overview) plus your own
  subject-line template and signature.
- **Optional unreached-people-group data.** A partner's public page can
  pull live country statistics from the
  [Joshua Project](https://joshuaproject.net/) — population, primary
  religion, percent evangelical, how reached the country is. Off by
  default; add a free API key and turn it on, no code changes.
- **White-labeling.** Three independently-pickable brand colors plus a
  font choice, and a custom term for "partners" (e.g. "Go Team Partners"
  instead of "Missionaries") used everywhere in the app that would
  otherwise say the hardcoded default.
- **Per-church feature toggles.** Turn off anything a church doesn't use;
  the toggle is enforced on the server, not just hidden in the UI.
- **Accounts with optional two-factor.** Email and password, with TOTP
  that an admin can require per account.
- **One-click deployment on [Render](https://render.com)** with a
  browser-based first-run setup, so standing up an instance needs no shell
  or database access. The blueprint asks for your service name and region
  rather than guessing; `npm run name-instance -- <name> <region>` sets
  both before you deploy. Pick the region deliberately — Render cannot
  change it afterwards without rebuilding the service.

If you're working on a fork, `npm run test:db up` builds a throwaway
Postgres in Docker, migrates and seeds it, so the test suite never touches
a database you care about. See [CONTRIBUTING.md](CONTRIBUTING.md).

Two things worth knowing before you run it:

- **The app refuses to start without a real `SESSION_SECRET`** (32+
  characters, not the example value). Anyone who knows that value can forge
  an admin session, and `.env.example` ships it empty so a fresh copy fails
  loudly rather than looking configured. `npm run generate-secrets` prints
  one.
- **Any account can read every partner's full record**, including
  restricted partners' exact locations and contact details. Roles control
  what someone can _change_, not what they can see. See
  [ADMIN_GUIDE.md § Who can see what](ADMIN_GUIDE.md#who-can-see-what)
  before handing out accounts.
